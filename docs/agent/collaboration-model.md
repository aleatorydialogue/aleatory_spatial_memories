# Agent collaboration model

## Objective

Use specialist agents to increase founder leverage while keeping product judgment, customer promises, and durable project memory coherent. Agents should own bounded work products, not competing versions of project strategy.

## Authority

The founder owns priorities, taste, customer relationships, commercial commitments, publication, legal decisions, and real-world execution. The lead development agent coordinates implementation, integration, validation, and documentation. Specialists investigate or produce clearly scoped artifacts and surface decisions for review.

No agent may turn a hypothesis, future idea, or unverified source into a public claim.

## Candidate specialist roles

- Product and customer research
- Brand voice and conversion copy
- Art direction and media production
- UX and accessibility
- Frontend and design systems
- Spatial media and WebGL
- Privacy and security
- QA and performance
- Capture operations and data workflow

Create a role only when there is a concrete independent task. One agent may cover several roles in early phases.

## Work boundaries

Every assignment should define an objective, governing context, owned files, dependencies, acceptance criteria, and explicit non-goals. Prefer parallel work when ownership does not overlap. One designated integrator resolves cross-cutting changes and runs final validation.

Avoid simultaneous edits to the same file. If overlap is unavoidable, assign one owner and have other agents provide findings rather than edits.

## Durable memory

- Product and brand truths belong in context documents.
- Accepted consequential choices belong in decision records.
- External evidence belongs in the reference register with provenance.
- Reusable procedures belong in project documentation or scripts.
- Agent transcripts, chain-of-thought, scratch notes, and orchestration logs are not durable documentation.

## Review gates

Founder review is required before:

- Changing positioning, audience priority, naming, or customer promise
- Publishing public copy or real customer material
- Selecting services that receive customer or lead data
- Defining consent, ownership, retention, or archival terms
- Incurring spend or creating external accounts
- Presenting experimental or future capabilities as available

Engineering review is required for integration behavior, privacy controls, accessibility, performance, and deployment changes. Review should use evidence and explicit acceptance criteria rather than agent consensus alone.

## Herdr use

Herdr should receive small, verifiable assignments using the task template. Use dependencies to sequence research, decision, implementation, and review. The repository—not the orchestration system—remains the source of durable project truth. Periodically consolidate accepted findings into documentation and discard obsolete task chatter.
