# Project documentation

This directory holds the durable operating context for the project. It should help a founder, contributor, or specialist agent understand not only what to build, but which statements are facts, decisions, hypotheses, or future ideas.

## Source-of-truth hierarchy

1. `PROJECT_BRIEF.md` governs vision, positioning, and strategic intent.
2. Accepted records in `decisions/` govern a specific decision within that vision.
3. Context documents describe the current working interpretation and known constraints.
4. Material in `references/` is evidence or inspiration, not project policy.
5. Task notes and agent conversations are temporary unless incorporated above.

When sources conflict, do not quietly choose one. Follow the higher-ranking source and document the conflict.

## Map

- `product/product-context.md` — proposition, audiences, offer, lifecycle, and current boundaries
- `brand/brand-context.md` — brand role, personality, and experience principles
- `brand/claims-and-terminology.md` — public-language and evidence guardrails
- `website/website-brief.md` — v0 site purpose, journey, content, and success criteria
- `technical/architecture.md` — intended application shape and system boundaries
- `technical/security-and-privacy.md` — required handling of leads and capture data
- `decisions/` — durable decision records and their status
- `agent/collaboration-model.md` — specialist ownership and coordination model
- `agent/task-and-handoff-template.md` — reusable assignment and handoff format

## Document status

Context documents represent the current working model, not immutable requirements. Mark unresolved items as `Open question`, proposed choices as `Proposed`, and established choices as `Accepted`. Changes that alter customer promises, business scope, privacy posture, or durable architecture require founder review.
